# Complexplorer rev3 closeout

Status: release candidate closeout plan  
Reviewed branch: `docs/openspec-baseline`  
Reviewed commit: `e63696a31dd9b9533fda9e65f241165aee3f89fd`

## Goal

Ship Complexplorer 3.0 as a coherent, trustworthy visualization library—not merely a
collection of finished features.

Rev3 already contains enough substantive work for a major release: a single PyVista 3D
backend, a shared surface kernel, Riemann surfaces, the function catalog and CLI, engineering
mode, a phase-wheel legend, and a smaller public API. The remaining work should be a feature
freeze focused on four outcomes:

1. **Show the library convincingly.** A visitor should understand the range and quality of
   rev3 within 30 seconds, before reading the API.
2. **Teach the supported workflows.** A new user should be able to reproduce every flagship
   image from a short, current example.
3. **Make the release contract honest.** Version, changelog, migration guidance, packaging,
   CI, and published documentation must agree.
4. **Remove visible scaffolding.** Public prose and metadata should describe the product that
   exists, not internal phases, future consumers, or obsolete backend plans.

## Release definition of done

Rev3 is ready when all of the following are true:

- [ ] The README opens with a representative rev3 visual—not a single legacy image—and a
      one-sentence description broad enough to include mathematical, engineering, and physical
      output.
- [ ] A curated visual tour demonstrates 2D portraits, phase-wheel legend, analytic landscape,
      Riemann sphere/relief, multivalued Riemann surface, engineering mode, and STL/physical
      output.
- [ ] Every flagship visual has a short runnable example and is generated by a documented
      command.
- [ ] Current, hosted rev3 documentation is ready to deploy with the package.
- [ ] A task-oriented 2.x → 3.0 migration guide covers every intentional break.
- [ ] The wheel and sdist—not only an editable checkout—pass installation and rendering smoke
      tests.
- [ ] Claimed Python versions and minimum dependency versions are enforced in CI.
- [ ] The final release commit passes tests, lint, formatting, OpenSpec validation, notebook
      execution, gallery regeneration, and artifact checks.
- [ ] Changelog date, tag, GitHub release, PyPI package, and hosted docs describe the same
      released version.

## Closeout finding: the published 2.0.0 baseline (added 2026-09-14)

PyPI carries **2.0.0** (uploaded 2025-10-19), built from tag `v2.0.0` on `main`. This branch
forked from `main` at `c892bdb` (2025-08-22, just after 1.0.1), so it has never contained 2.0.
Measured against what users actually have installed, rev3 removes:

- 10 colormaps (`OklabPhase`, `PerceptualPastel`, `AnalogousWedge`, `DivergingWarmCool`,
  `Isoluminant`, `CubehelixPhase`, `InkPaper`, `EarthTopographic`, `FourQuadrant`, plus OkLCh
  gamut clipping)
- the published `n_phi → phase_sectors` rename
- the logging API
- 12 exception classes
- `show` and the `*_preset` helpers
- the MkDocs Material site, live on `gh-pages`
- 12 notebooks, including `05_accessibility_cvd`

The CHANGELOG claim that 2.0 was "never published" is false.

**Decisions:**
- Rev3 stays the trunk, and assets worth keeping are ported selectively.
- `phase_sectors` is canonical.
- The migration guide covers **2.0.0 → 3.0**.
- Histories are joined at release with `git merge -s ours origin/main`.
- Visual review runs through a private review page.
- Printed-ornament photos are supplied by the owner.

# P0 — complete before release

## 1. Make the visual showcase a release gate

Complexplorer is a visualization library. The images are not decorative documentation; they
are primary evidence that the package works and the fastest explanation of why it exists.

The current generated gallery is a strong asset base:

- 17 phase portraits
- 7 analytic landscapes
- 7 Riemann spheres
- 3 multivalued Riemann surfaces
- 2 ornament/relief renders
- 8 colormap examples

However, that asset count overstates the breadth currently *shown*. Several rev3 headline
capabilities are absent from the gallery, and the generated page presents many full-size images
in a long vertical stream rather than as a curated tour.

### 1.1 Create a “rev3 at a glance” hero montage

- [ ] Replace or supplement the current single hero image with a clean 2×3 montage.
- [ ] Keep it readable at normal GitHub README width; avoid tiny labels and large unused margins.
- [ ] Use one visual for each distinct idea rather than six variants of the same function.
- [ ] Use consistent backgrounds, crops, typography, camera conventions, and output dimensions.
- [ ] Include concise labels in the montage or an immediately adjacent caption.
- [ ] Verify the montage renders correctly on GitHub and the PyPI project page.

Recommended panels:

| Panel | Capability to prove | Suggested content |
|---|---|---|
| 1 | Domain coloring | `(z² - 1)/(z² + 1)` with the phase-wheel legend visible |
| 2 | Analytic landscape | The same function, making the 2D → 3D relationship obvious |
| 3 | Riemann sphere or relief | `z/(z¹⁰ - 1)` or another visually distinctive full-sphere render |
| 4 | Multivalued surface | `sqrt(z)` or `log(z)`, with a view that clearly exposes sheet structure |
| 5 | Engineering mode | Transfer-function portrait with poles, zeros, stability boundary, and legend |
| 6 | Math to matter | Rendered ornament beside a photograph of the printed object |

The montage should communicate the umbrella proposition: **visual exploration of complex
mappings—from domain coloring and multivalued geometry to transfer functions and physical
objects.** Keep “transform complex mathematics into tangible art” as the secondary tagline.

### 1.2 Add the missing flagship visuals

- [ ] **Phase-wheel legend:** generate at least one committed portrait with `legend=True`.
      The legend is a rev3 feature and currently is described but not visibly demonstrated.
- [ ] **Engineering mode:** add a compact showcase for one nontrivial stable transfer function.
      At minimum show `transfer_portrait`; ideally present the portrait, pole-zero map, Bode
      plot, and Nyquist plot as one coherent figure or tightly grouped set.
- [ ] **Composition proof:** show that the same `TransferFunction` object works in a standard
      Complexplorer renderer, preferably a transfer portrait beside a 3D landscape.
- [ ] **Composite domains:** add one image whose geometry visibly depends on union,
      intersection, or difference. The feature is currently claimed but not shown.
- [ ] **Riemann surface versus Riemann sphere:** add a side-by-side explanation. The current
      prose distinction is good, but the visual distinction should be immediate.
- [ ] **STL to physical print:** show the generated relief, mesh/STL view, and a real printed
      object. This is the strongest evidence for the “math to matter” identity.
- [ ] **Interactivity:** produce one short, restrained loop of a rotating Riemann surface or
      relief. A static screenshot cannot prove rotation, zoom, lighting, or depth perception.
      Use this in the documentation/release post; embed it in the README only if size and
      loading behavior remain reasonable.

### 1.3 Turn the gallery into a curated visual tour

- [ ] Add a compact table of contents or thumbnail grid at the top of the gallery.
- [ ] Organize by idea rather than registry order: phase portraits; mapping and topology;
      Riemann surfaces; engineering; colormaps; physical output.
- [ ] Use thumbnail/card views that link to full-resolution images. Do not make readers scroll
      through roughly 45 full-size images to discover the range.
- [ ] Give each flagship figure a one- or two-sentence interpretation: what mathematical
      structure is visible and what rendering mode reveals it.
- [ ] Keep runnable code adjacent to the corresponding visual, but collapse or de-emphasize
      repetitive boilerplate.
- [ ] Add useful alt text. Current generated alt text often repeats only the preset title and
      does not distinguish portrait, landscape, sphere, surface, or ornament.
- [ ] Ensure every generated page clearly says which source file to edit and which command
      regenerates it.
- [ ] Add engineering, composite-domain, and phase-wheel assets to the presentation manifest,
      even if they do not naturally belong in `cp.catalog`.

### 1.4 Establish visual quality criteria

- [ ] Define canonical camera, background, lighting, axes, window size, and antialiasing
      settings for each PyVista render family.
- [ ] Inspect the sphere seam/poles and Riemann-surface intersections at full resolution.
- [ ] Check color fidelity and contrast in both light and dark browser themes.
- [ ] Confirm labels and legends remain legible after README/PyPI scaling.
- [ ] Avoid clipped peaks, excessive empty margins, unreadable orientation widgets, and views
      where sheet structure collapses into a flat silhouette.
- [ ] Record the function, domain, colormap, scaling, resolution, and camera used for each
      curated asset.
- [ ] Decide which images are deterministic build outputs and which are hand-curated release
      assets. The `index.json` manifest is byte-stable; PNGs are currently best-effort and
      should not be described as byte-identical.
- [ ] Regenerate the gallery from a clean checkout and review the actual diff before tagging.

### 1.5 Create a short visual narrative for the release

A useful five-step story is:

1. **See a complex function** as a phase portrait.
2. **Read the image** using the phase-wheel legend.
3. **Lift magnitude into geometry** as a landscape or Riemann relief.
4. **Resolve multivalued behavior** on a Riemann surface, or apply the same machinery to an
   engineering transfer function.
5. **Export the geometry** as an STL and make it physical.

- [ ] Build the documentation landing page and release announcement around this sequence.
- [ ] Ensure each step uses a minimal public-API snippet that runs as printed.
- [ ] Do not make the catalog, CLI, or surface kernel compete with the visual story. Present
      them as the machinery that makes the story reproducible and composable.

## 5. Enforce an artifact-level release gate

The current CI installs the source editable with `uv pip install -e ".[dev]"`. The hardening
OpenSpec records a successful one-time wheel smoke test, but this is not yet enforced in the
workflow.

- [ ] Add a CI job that runs `python -m build` (or `uv build`).
- [ ] Run `twine check dist/*` or the equivalent metadata validation.
- [ ] Create a fresh environment and install the built wheel, not the working tree.
- [ ] From the installed wheel, run:
  - [ ] `import complexplorer as cp; print(cp.__version__)`
  - [ ] `complexplorer list`
  - [ ] one 2D file render
  - [ ] one real off-screen PyVista landscape or sphere render
  - [ ] one small STL export
- [ ] Inspect wheel/sdist contents: `py.typed`, both license files, expected subpackages, and no
      examples/tests/build debris.
- [ ] Inspect wheel metadata: version, `Requires-Python`, dependencies, license expression,
      classifiers, URLs, and console entry point.
- [ ] Test the sdist path at least once by building a wheel from the sdist in a clean
      environment.

## 6. Align CI with the compatibility claims

- [ ] Add one macOS lane, especially because PyVista/VTK is required.
- [ ] Add an Ubuntu/Python 3.11 minimum-dependency job that installs the declared lower bounds:
      NumPy 1.26, matplotlib 3.8, SciPy 1.11, asteval 1.0, and PyVista 0.47.
- [ ] Keep the ordinary matrix on current dependencies to catch upstream breakage.
- [ ] Add notebook execution to CI or a required pre-release workflow. The notebooks are core

- [ ] Add a gallery structural check that regenerates into a temporary directory and verifies

## 8. Remove or substantiate brittle marketing claims

- [ ] Replace “first library to…” claims unless priority can be documented responsibly.
- [ ] Replace “15–30x faster” with “high-performance” unless a reproducible benchmark, baseline,
      hardware description, and tested version range are published.
- [ ] Replace “cinema-quality output” with a concrete capability such as configurable lighting,
      antialiasing, high-resolution screenshots, or interactive navigation.
- [ ] Replace “no supports needed” with “designed for FDM printing” plus tested orientation,
      minimum thickness, and support caveats. Printability depends on function, geometry,
      printer, material, and slicer settings.
- [ ] Audit the README, changelog, PyVista guide, package metadata, and release announcement so
      softened wording is consistent everywhere.

## 9. Finish the public typing contract

Shipping `py.typed` invites downstream type checkers to rely on annotations. Concentrate on the
public API rather than attempting to type every implementation detail.

- [ ] Introduce a canonical type/Protocol for vectorized complex functions; current
      `Callable[[complex], complex]` on `quick_plot` does not describe functions called with
      NumPy arrays.
- [ ] Type `FunctionPreset.func`, domain/colormap/scaling specs, singularity records, and catalog
      return values more precisely.
- [ ] Add explicit public return types for `quick_plot`, `Presets` methods, engineering plotting
      functions, CLI resolution helpers that are part of tested behavior, and gallery APIs.
- [ ] Replace broad bare `dict`, `tuple`, and `Callable` annotations on public contracts with
      aliases, `TypedDict`, or Protocols where that improves user feedback.
- [ ] Decide how scalar-versus-array return behavior of `TransferFunction.__call__` should be
      represented and document it.
- [ ] Add a small Pyright or mypy gate over the package's public surface.
- [ ] Add one downstream-style typing fixture that imports the installed wheel.

## 10. Resolve naming and API discoverability

- [ ] Make a final explicit decision on `cp.Presets` versus `cp.catalog`. The distinction is
      defensible, but it is not immediately obvious.
- [ ] If preserving compatibility, keep the names and teach the distinction everywhere with one
      sentence: **`Presets` configures a render; `catalog` supplies a function.**
- [ ] If renaming `Presets` to `PlotPresets`, do it now, during the major release, with a clear
      migration note. Do not carry both names indefinitely without a deprecation policy.
- [ ] Add a compact top-level API map to the docs so users can find the recommended entry point
      for 2D, 3D, sphere, surface, engineering, gallery, and STL workflows.
- [ ] Confirm every name in `complexplorer.__all__` is documented, typed, and intentionally
      public.
- [ ] Clarify return contracts (`Axes`, `Figure`, `Plotter`, mesh, path, or `None`) across the
      renderer docs.

## 11. Add professional repository metadata

- [ ] Add `CONTRIBUTING.md`: environment setup, editable install, tests, Ruff, OpenSpec workflow,
      notebook execution, gallery regeneration, and artifact checks.
- [ ] Add `CITATION.cff` so GitHub exposes “Cite this repository” with structured authorship and
      version metadata.
- [ ] Replace the README's hard-coded `year = {2024}` citation or generate the BibTeX guidance
      from the CFF metadata.
- [ ] Expand `[project.urls]` with Documentation, Source, Changelog, and Release notes.
- [ ] Add a support route: GitHub Discussions, Issues, or a short support policy.
- [ ] Add issue templates for bug reports and visual/rendering problems; collect OS, Python,
      PyVista/VTK versions, backend, GPU/display context, and a minimal function/domain example.

## 12. Revisit the mandatory PyVista decision once, then close it

PyVista/VTK is now installed for every user, including those who only want a 2D phase portrait.
The architectural benefit is real, but the dependency and import cost are material.

- [ ] Record the decision explicitly: required PyVista versus an optional `3d` extra with lazy
      imports.
- [ ] Measure wheel/install size and cold `import complexplorer` time on at least one clean
      environment.
- [ ] Test installation on the three supported operating systems.
- [ ] If PyVista remains required, explain the rationale once in the backend policy and remove
      all residual optional-backend language.
- [ ] If it becomes optional, restore the boundary cleanly rather than reviving scattered
      `HAS_PYVISTA` flags.

This is the highest-cost architectural choice to reverse later; it deserves a conscious final
decision, not repeated uncertainty after release.

## 13. Polish accessibility and output behavior

- [ ] Ensure legends do not obscure important singularities or get clipped when saving figures.

- [ ] Document how users obtain deterministic camera views and reproducible screenshots.
- [ ] Confirm warnings and validation errors name the invalid value, accepted values, and the
